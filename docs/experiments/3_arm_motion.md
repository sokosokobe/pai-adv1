# #3 アームの動作計画

- **Issue**：#3
- **日付**：2026-10-03
- **タイムボックス**：3時間 ／ **実績**：約0.5時間（15:09〜15:37）
- **検証用コード**：`scripts/experiments/arm_reach.py`（届く範囲）、`scripts/experiments/arm_motion.py`（動作の比較）、共通部分 `arm_sim.py`。Isaac Sim 非依存の計算は `arm_common.py`（単体テスト `tests/experiments/test_arm_common.py`）
- **証拠**：`outputs/m0_3/reach/reach.json`、`outputs/m0_3/motion/`（`summary.json`、各試行の画像）

## 目的

1. Isaac Sim 6.1 で使える動作計画の手段のうち、どれを使うか
2. cuMotion 同梱の Franka 単体用の設定を、RidgebackFranka のアームにそのまま使えるか（関節名、台車の関節、アームの根元の位置の渡し方）
3. 台車を原点以外に置いたとき、台車を動かした後に、机の上の目標へ正確に・衝突なく届くか
4. アームが楽に届く範囲（台車から物体までの距離の目安）

## 方法

- Isaac Sim 6.1.0（pip 版）、headless、物理 60Hz。RidgebackFranka は Multiphysics 版、台車の x・y 関節の `physxJoint:jointFriction` は 0（#2 の決定事項）
- **到達範囲**（`arm_reach.py`）：台車を原点・向き 0 に置き、台車座標系の格子点（台車の中心からの水平距離 0.3〜1.1m × 手先の高さ 0.2〜1.1m × 方向 -90〜+90°、計 630 点）について、cuMotion の衝突を考えた IK（`CollisionFreeIkSolver`）を解いた。障害物は地面と台車本体（箱で近似）。手先（`panda_hand`）を真下に向ける場合と、位置だけの場合の2通り
- **動作の比較**（`arm_motion.py`）
  - 台車の姿勢 A = (1.0, -0.5, 30°)。机（固定、奥行き 0.6 × 幅 1.2 × 高さ 0.7 m）を台車 A の前面から 8cm 空けて置いた
  - 目標 5点：台車 A から見て (距離, 方向) = (0.65m, 0°), (0.80m, 0°), (0.70m, +25°), (0.70m, -25°), (0.75m, +35°)、手先の高さ 0.85m（指先は天板の約 4cm 上）、手先は真下向き
  - 各試行の前にアームを待機姿勢に戻す（下の「分かったこと」の 3. を参照）
  - 段階：**A**（根元の姿勢を cuMotion に渡す）→ 台車を #2 の速度指令で姿勢 B（A から机に沿って左へ 0.3m、向き -10°）へ移動 → **B・根元を更新しない** → **B・根元を更新する**
  - 成功の判定：最終の位置誤差 1cm 以内、姿勢誤差 5° 以内。所要時間は誤差がこの範囲に入り、以後ずっと入ったままになった時刻
  - 接触：アームのリンクに PhysX の接触レポートを付け、机・台車本体との接触を記録した。接触レポートは接触判定のマージン内の「近接」も報告するので、めり込み 1mm 以上または力積が 0 でないものだけを「接触」とした

## 結果

### 1. 6.1 で使える手段の整理

| 手段 | 状態 | 今回の扱い |
|---|---|---|
| Motion Generation（Experimental）`isaacsim.robot_motion.experimental.motion_generation` | 6.1 の新しい共通の枠組み（コントローラ・軌道・WorldBinding・RobotState などのインターフェース）。単独の計画器ではない | 枠組みとして使った |
| cuMotion `isaacsim.robot_motion.cumotion` | 6.1 に同梱。上の枠組みの実装で、**RmpFlowController**（反応型）、**TrajectoryOptimizer**（軌道最適化）、**GraphBasedMotionPlanner**（グラフ探索）、**CollisionFreeIkSolver**（衝突を考えた IK）を持つ。6.1 の Franka Pick and Place サンプルは RmpFlowController を使っている | 3つの計画器を比較 |
| Lula（RMPflow / RRT） | 6.1 では `extsDeprecated/` 配下（非推奨） | 除外 |
| cuRobo | 6.1 に同梱されておらず、venv にも入っていない。公式の対象は Linux | 除外（導入はしていない。Windows での導入可否も未確認） |

### 2. Franka 用の設定を RidgebackFranka に使う方法

cuMotion 同梱の Franka 設定（`load_cumotion_supported_robot("franka")`）をそのまま使えた。必要だったのは次の 4点。

1. **アームの根元の姿勢**：設定の根元のリンク `base_link` は `panda_link0` と同じ位置・向き（URDF の `base_link_robot` は恒等変換）。RidgebackFranka では **`panda_link0` のワールド姿勢を `CumotionWorldInterface.update_world_to_robot_root_transforms` に渡す**。Franka 単体のサンプルは `articulation.get_world_poses()` を渡しているが、RidgebackFranka のアーティキュレーションの根元はワールドに固定された `world` リンクなので、それでは誤り。台車の上の `panda_link0` は台車の中心から 0.30m 前方、高さ 0.28m
2. **関節の対応**：`robot_joint_space` に**全 12 DOF の名前**を渡すと、計画結果のインデックスがそのまま Articulation の DOF 番号になる（台車の 3 関節は cuMotion の制御対象外として無視される）。cuMotion が制御するのは `panda_joint1`〜`7` の 7 関節
3. **tool frame を明示する**：設定の tool frame は `["panda_leftfingertip", "panda_hand"]` の順。`TrajectoryOptimizer` と `GraphBasedMotionPlanner` は `tool_frame` を省略すると先頭の **指先**（`panda_leftfingertip`）を使い、手先の目標が 10.7cm・180° ずれた（最初の試行で全失敗）。`tool_frame="panda_hand"` を明示して解消
4. **台車本体を障害物に加える**：cuMotion の衝突モデルはアームだけ。台車本体（`base_link` の外形、0.93 × 0.79 × 0.26 m）を `add_cubes` で箱の障害物として加え、台車が動いたら `update_obstacle_transforms` で動かす（`ArmPlanning.sync()`）

- 所要時間は「動き始めてから誤差 1cm・5° 以内に収まるまで」。TrajectoryOptimizer と GraphBasedMotionPlanner は、これに計画時間が加わる（合計：TrajectoryOptimizer 約 1.05s、GraphBasedMotionPlanner 約 1.26s、RMPflow 約 1.2s）
- **根元の更新は必須**：更新しないと、RMPflow と GraphBasedMotionPlanner は台車の移動量（約 0.3m・10°）だけずれた位置へ動く（誤差 185〜201mm・10°）
- ※ TrajectoryOptimizer が更新しなくても成功したのは、目標を根元基準に変換するときに、検証コード側でシミュレーションから読んだ最新の `panda_link0` の姿勢を使ったため。cuMotion 内部の障害物（机・台車）の位置は古いままなので、衝突を避けられる保証はない。どの手段でも、台車が動いたら `sync()` を呼ぶ
- **接触は 0 回**（全 45 試行）。「近接」は TrajectoryOptimizer で 2 回だけで、どちらも肘（`panda_link3`）が机まで 1.2cm・1.7cm に近づいたもの
- **再現性**：同じ条件で 2 回実行すると、RMPflow は同じ結果（差 0.001 未満）、GraphBasedMotionPlanner はほぼ同じ（姿勢誤差で 0.003° 程度の差）だった。TrajectoryOptimizer は**実行のたびに軌道が少し変わる**（同じ目標で軌道の長さが最大 0.28s 違った）。成功・失敗と接触の有無は変わらなかった
- 画像：`outputs/m0_3/motion/<段階>_t<目標番号>_<手段>.png`（試行後）、`<段階>_start.png`（待機姿勢）。目標は緑の立方体。目視で、成功した試行では手先が真下を向いて目標の真上にあること、根元を更新しない RMPflow では目標から外れた位置で止まっていることを確認した

## 結論

1. **cuMotion 同梱の Franka 設定は RidgebackFranka のアームにそのまま使える**。ただし「`panda_link0` の姿勢を根元として渡し、台車が動くたびに更新する」「全 DOF の名前で関節を対応させる」「tool frame に `panda_hand` を明示する」「台車本体を障害物として加える」の 4 点が必要
2. 3 つの計画器とも、台車を原点以外に置いた場合・台車を動かした後（根元を更新）の両方で 15/15 成功し、誤差は 1mm 程度、接触はなかった。精度・成功率では差がつかなかった
3. **動作計画の手段の推奨案：cuMotion の RmpFlowController（Motion Generation の枠組みで使う）**
   - 選んだ理由
     - 6.1 の Franka Pick and Place サンプルの構成（`PickPlaceController`：真上へ移動 → 下降 → 把持 → 持ち上げ → 移動 → 配置、と指の開閉）が RmpFlowController の上に作られており、#4（把持と配置）でそのまま参考にできる
     - 反応型で計画の待ち時間がなく、結果が決定的（同じ条件で同じ動き）。台車の姿勢の更新を毎ステップ反映でき、移動マニピュレータと相性がよい
     - 所要時間（約 1.2s）・精度（1mm 以下）は他の手段と同等
   - 選ばなかった案
     - TrajectoryOptimizer：最も正確（0.3〜0.4mm）で、計画を含めた合計時間も最短（約 1.05s）。ただし毎回軌道が変わり、目標を根元基準に変換する手間がある。**棚の中など障害物が込み入った場面で RMPflow が局所解に陥った場合の代替**として残す
     - GraphBasedMotionPlanner：計画は最速（0.05s）だが、経路を軌道に変換する上限速度などを自分で決める必要があり、利点が少ない
4. **アームが楽に届く範囲は、台車の正面で中心から 0.55〜0.85m（前面から 0.1〜0.4m）、手先の高さ 0.4〜0.9m**

## 設計への影響

- **アームの制御**は `src/restorebot/sim/` に置き、cuMotion の RmpFlowController を Motion Generation の枠組みで使う。今回の `ArmPlanning`（`arm_sim.py`）の 4 つの処理（根元の更新、全 DOF の名前での対応、tool frame の明示、台車の障害物）は、本実装でも必ず入れる
- **台車が動いたら必ず `sync()`（根元・台車の障害物・周囲の物体の更新）を呼ぶ**。忘れると 20cm・10° ずれる
- **台車用の待機姿勢が必要**：Franka 単体の既定姿勢（Pick and Place サンプルの `default_joint_positions`。cuMotion の xrdf の既定値とは少し違う）は、RidgebackFranka ではアームの根元が低い（0.28m）ため、手先が高さ 0.7m の机の天板に当たる。今回は「台車座標で (0.4, 0, 0.95) に手先を真下に向けた姿勢」を衝突を考えた IK で求めて使った（`panda_joint1`〜`7` = -1.261, -1.378, 0.182, -2.254, 0.229, 0.892, 0.228 rad）。移動中もこの姿勢にしておく
- **台車の止め方（ナビゲーション層への条件）**：物体が台車の正面、中心から 0.55〜0.85m（前面から 0.1〜0.4m）に来るように止める。机は台車の前面の近く（10cm 程度）まで寄せる必要がある。物を置く机・棚の高さは、手先の高さ 0.4〜0.9m に収まる範囲（天板 0.3〜0.75m 程度）を想定する
- **未解決・申し送り**
  - 物を持った状態、指の開閉、持ち上げ後の移動は #4 で確認する（6.1 の `PickPlaceController` を参考にする）
  - 障害物が込み入った場面（棚の中など）での RMPflow の振る舞いは未確認。問題があれば TrajectoryOptimizer に切り替える
  - cuRobo は Windows での導入可否を含めて未確認
  - 今回の目標はすべて手先を真下に向けた姿勢。横からつかむ姿勢は試していない
