# #5 天井カメラと VLM による差分検出

- **Issue**：#5
- **日付**：2026-10-12
- **タイムボックス**：3時間 ／ **実績**：約1.2時間（14:55〜16:05）
- **検証用コード**：`scripts/experiments/vlm_scene.py`（部屋と画像のペアの生成、Isaac Sim）、`vlm_clients.py`（3 つの VLM の呼び出し）、`vlm_eval.py`（評価）、`vlm_checks.py`（残像と Qwen の位置の精度の確認）。配置の生成・投影・プロンプト・応答の解析・照合は `vlm_common.py`（単体テスト `tests/experiments/test_vlm_common.py`）
- **証拠**：`outputs/m0_5/dataset*/`（画像・深度・正解データ・正解を重ねた画像）、`outputs/m0_5/eval/<run>/`（応答の全文 `results.jsonl`、集計 `summary.md`、予測を重ねた画像 `overlay/`）

## 目的

1. 「いつもの写真」と「今の写真」から、VLM が動いた物体と戻し先を特定できるか
2. 天井カメラ（RGB＋深度）の位置・画角・解像度をどうするか
3. どの VLM を使うか（精度・速度・費用、ローカルで動くか）
4. 結果を JSON で受け取るプロンプトと形式

## 方法

### 部屋と物体（`vlm_common.py`、`vlm_scene.py`）

- Isaac Sim 6.1.0（pip 版）、headless。物理演算は使わず、物体を置き場所に直接置いて描画だけ行う
- 部屋：床 3.2m × 2.4m、壁の高さ 2.4m。机（1.2 × 0.6m、天板の高さ 0.72m）と棚（0.4 × 1.0m、天板の高さ 0.8m）。どちらも単純な箱
- 物体（5 個、色と形で見分けられる）

  | 名前 | 形 | 大きさ | いつもの場所 |
  |---|---|---|---|
  | 赤いマグカップ | 円柱 | 直径 9cm × 高さ 10cm | 机の左 |
  | 黄色い本 | 平たい箱 | 24 × 17 × 3.5cm | 机の中央 |
  | 青い箱 | 箱 | 18 × 12 × 8cm | 机の右 |
  | 緑のボール | 球 | 直径 12cm | 棚の奥 |
  | 紫のコーン | 円錐 | 底面の直径 12cm × 高さ 14cm | 棚の手前 |

- 照明はドームライト（1000）だけ。真下からの平行光源も試したが、床に光源の映り込み（白飛び）が出たのでやめた
- 画像の向きの目印：床の左上の隅（-x, +y）に黒い板を置いた

### 天井カメラ

- 天井の中央、高さ 2.6m に真下向き（回転なし：カメラの -Z がワールドの -Z、画像の上がワールドの +y、右が +x）
- 焦点距離 13.5mm、水平アパーチャ 20.955mm（水平画角 75°）、解像度 1024 × 768、正方画素。床の約 4.0 × 3.0m が写る（1 ピクセルは床の上で約 3.9mm、机の上で約 2.8mm）
- RGB と深度（`distance_to_image_plane`）を `isaacsim.sensors.experimental.rtx.CameraSensor` で取得
- 正解の画像上の座標は、ピンホールモデルで投影して求めた（`DownCamera.project`）。fx = 焦点距離 / 水平アパーチャ × 幅 = 659.7px

### 画像のペア（シード固定）

- `easy`（シード 0、10 組）：1〜3 個を選び、置き場所（床 60%・机 20%・棚 20%）を選び直して、元の位置から 40cm 以上離す。向きはランダム
- `small`（シード 1、10 組）：1〜3 個を、同じ面の上で 10〜25cm だけずらす。向きはランダム
- どちらも物体どうしが重ならず、置き場所の縁から 2cm 以上離れるようにした

### VLM と問い合わせ方

| | Gemini Robotics-ER 2 | Claude Sonnet 5.5 | Qwen3-VL 8B |
|---|---|---|---|
| モデル | `gemini-robotics-er-2-preview` | `claude-sonnet-5-5` | `qwen3-vl:8b-instruct-q8_0`（8 ビット量子化） |
| 実行場所 | Google のクラウド | Anthropic のクラウド | ローカル（Ollama 0.40.3、RTX 5070） |
| SDK・API | `google-genai` 2.29 | `anthropic` 0.125 | Ollama の `/api/chat` |
| 座標の形式 | [y, x]、0〜1000 に正規化（モデル本来の形式） | [x, y]、ピクセル | [x, y]、0〜1000 に正規化（モデル本来の形式） |
| 出力の形式 | JSON モード（`response_mime_type`） | 構造化出力（JSON スキーマ） | 構造化出力（JSON スキーマ） |
| 思考 | `thinking_level=medium`（公式の推奨） | adaptive、`effort=high`（既定） | なし（Instruct 版） |
| 料金（100万トークンあたり） | 入力 $1、出力 $5（2026 年末まで。無料枠あり） | 入力 $2、出力 $10 | 0（電気代のみ） |

- 1 回の問い合わせで、1 枚目に「いつもの状態」、2 枚目に「今の状態」の画像を渡す
- プロンプトは 2 種類：物体名のリストを渡す（`names`）／渡さない（`nonames`）

### 評価（`evaluate`、`aggregate`）

- `names`：予測した名前で正解の物体と照合する（空白・全角半角・大文字小文字の違いは無視）
- `nonames`：名前の表記が揺れるので、予測した「今の位置」に最も近い物体（40px 以内）と照合する
- 動いた物体に照合されたものを正しい検出、動いていない物体・どの物体にも当たらないもの・同じ物体への 2 回目以降の予測を誤検出、照合されなかった動いた物体を見落としとした
- 戻し先：予測した戻し先と正解（いつもの画像での中心）の距離が 40px（床で約 16cm、机の上で約 11cm）以内なら OK
- 完全一致：見落としも誤検出もなかったシナリオの割合

### プロンプト（座標がピクセル、物体名のリストを渡す場合）

`build_prompt` で作る。英語で指示し、名前と場所の説明は日本語で答えさせる。座標の説明の 1 文だけをモデルに合わせて変え、物体名のリストを渡さない場合は「色＋物の種類の短い日本語の名前」を付けさせる。全 6 種類は `outputs/m0_5/eval/easy/prompt_*.txt`。

```text
You are given two top-down images of the same room, taken by the same fixed ceiling camera.
Image 1 is the REFERENCE: the usual, tidy state of the room.
Image 2 is the CURRENT state. Some objects have been moved from their usual places.

Task: list every object whose position in the CURRENT image differs from its position in the REFERENCE image.
Do not list objects that stayed in place. Furniture (desk, shelf) and walls never move.

The room contains these movable objects. Use exactly one of these names for `name`:
- 赤いマグカップ
- 青い箱
- 緑のボール
- 黄色い本
- 紫のコーン

For each moved object, report:
- current_location: where it is now (short Japanese description, e.g. 床の右下, 机の上の左端)
- current_point: the center of the object in the CURRENT image
- target_location: where it should be returned to (short Japanese description)
- target_point: the center of the object in the REFERENCE image (its usual place)

Points are [x, y] in pixels of the 1024x768 image: origin at the top-left corner, x increases to the right, y increases downward.

Respond with JSON only, in this format:
{"moved_objects": [{"name": "...", "current_location": "...", "current_point": [0, 0], "target_location": "...", "target_point": [0, 0]}]}
```

### JSON の形式（案）

```json
{"moved_objects": [
  {"name": "黄色い本",
   "current_location": "右の机の上の中央上寄り(回転している)", "current_point": [769, 101],
   "target_location": "右の机の上の中央", "target_point": [797, 152]}
]}
```

- `current_point`：今の画像での物体の中心。`target_point`：いつもの画像での中心（＝戻し先。カメラが固定なので、同じ座標が今の画像でもそのまま使える）
- 座標の形式はモデルごとに違うので、プロンプトで指定し、受け取ったらクライアントの境界でピクセル (u, v) にそろえる（`to_pixels`）。設計では、ピクセルにそろえた後の形を正とする
- JSON スキーマは `RESPONSE_SCHEMA`（`additionalProperties: false`、5 項目すべて必須）。Claude と Qwen には構造化出力で強制し、Gemini には JSON モードだけを使った。どのモデルでも解析の失敗は 0 回だった
- 戻し先の 3 次元位置は、`target_point` の画素の深度（いつもの画像の深度）とカメラの内部パラメータから逆投影して求められる（M3 で使う）

## 結果

### 1. カメラと画像の向き

- 画像の向きは正しい：床の左上の隅（-x, +y）に置いた目印は画像の左上に、机（+x, +y）は右上に、棚（-x）は左に写った（`outputs/m0_5/dataset/tidy_rgb.png`）
- 投影も正しい：正解を重ねた画像（`dataset*/overlay/`）で、円が物体の中心に重なることを目視で確認した。深度の確認では、物体の上端の中心を投影した画素の深度と「カメラの高さ − 上端の高さ」の差が、上面が平らな物体（箱・円柱）と球で **0.000m**（全 22 枚 × 5 物体）。円錐だけ、頂点（面積がない）の画素の視線が頂点をかすめて床に当たり、差が円錐の高さ（0.14m）になった枚がある
- 床（3.2 × 2.4m）、机、棚、部屋の四隅がすべて写る。家具の側面は遠近で斜めに写る

**生成の途中で直したこと**

- **残像**：物体を動かした後、30 フレームだけ進めて撮ると、前のシーンの物体がうっすら残った（RTX の時間方向の処理によるもの。scene_07 に、scene_06 で床に置いた黄色い本の跡が写った。いつもの画像との差は平均 2〜4 階調）。150 フレーム進めると 0.2〜1.2 階調になり、物体のない床どうしの差（0.3〜0.8 階調）と同じ程度まで下がった。目視でも跡は消えた（`vlm_checks.py ghost`、`outputs/m0_5/checks/ghost_*.txt`）。評価は 150 フレームで作り直したデータセットで行った
- **照明**：真下からの平行光源は、床の中央に光源の映り込み（白飛び）を作ったので、ドームライトだけにした

### 3. Qwen3-VL 8B が弱い理由

- **2 枚目（今の画像）での位置がずれる**：正しく検出した物体の「今の位置」の誤差は、中央値 49px、最大 209px だった（easy、名前あり）。一方で、同じ今の画像を **1 枚だけ** 渡して物体を指させると、誤差は中央値 5.3px、最大 17.8px だった（5 枚 × 5 物体。`vlm_checks.py qwen-single`、`outputs/m0_5/checks/qwen_single.txt`）。比べる処理と位置を答える処理を 1 回で行うと、位置の精度が落ちる。名前なしの評価は位置で照合するので、このずれで「誤検出＋見落とし」になった
- **小さな移動を見落とす**：small では、名前ありでも再現率が 0.39 だった
- **ときどき大きく外れる**：戻し先の誤差が最大 599px
- **GPU のメモリ**：Q8_0 は Ollama で約 10GB（12GB の GPU に入りきらず、9% を CPU で実行）。Isaac Sim と同時には動かせない。Q4_K_M（6.1GB）なら全体が GPU に入るが、精度は試していない

### 4. 環境の問題（記録）

- **スマート アプリ コントロール**：この PC では Windows のスマート アプリ コントロールがオンで、署名のない実行ファイルや DLL を阻止する
  - llama.cpp の配布バイナリ（b11557、CUDA 13.4 版）は起動できなかった（終了コード 0xC0E90002）。署名のある Ollama（Ollama Inc.）は動いたので、Qwen は Ollama で動かした
  - `.venv` の torch も、`torch\lib\shm.dll` が阻止されて import できない。Isaac Sim の起動時に出る、非推奨の拡張機能（`isaacsim.core.api` など）の読み込みエラーはこれが原因。これまでの Issue のスクリプトは torch を使っていないので影響はなかった
- **依存関係**：`anthropic` 1.x は `httpx2` を通じて `idna>=3.18` を必要とし、Isaac Sim（`isaacsim-kernel`）の `idna==3.10` と衝突する。`anthropic` は 0.125（0.x の最新、`httpx` を使う）に留めた。`pip check` でエラーがないことを確認した

## 結論

1. **VLM で、動いた物体と戻し先を特定できる**。Claude Sonnet 5.5 と Gemini Robotics-ER 2 は、40cm 以上の移動でも 10〜25cm の小さな移動でも、動いた物体を見落としも誤検出もなく特定し、戻し先を画像上で 2〜4px（約 1cm）の精度で答えた
2. **天井カメラ**：高さ 2.6m、真下向き、水平画角 75°、1024 × 768。部屋全体が写り、物体（約 10cm）は 25px 前後で写る。この解像度で十分だった
3. **VLM の推奨は Claude Sonnet 5.5**（`claude-sonnet-5-5`、`effort=high`）
   - 精度は Gemini と同じ（どちらも満点）で、**応答が 2.5〜3 倍速い**（中央値 2.8〜3.0 秒、Gemini は 7〜10 秒）。デモでは、写真を撮ってからロボットが動き出すまでの待ち時間が短いほうがよい
   - 費用は 1 回 $0.0075 と、Gemini（$0.008〜0.012）と同じ程度。どちらもデモで問題にならない
   - 構造化出力で JSON の形式が保証される。Gemini Robotics-ER 2 はプレビュー版（仕様が変わる可能性があり、2027 年から料金が 2 倍になる）
   - **Gemini Robotics-ER 2 は代わりの候補**として残す。精度は同等で、無料枠があり、ロボット向けの機能（把持点の指示など）を後で使える可能性がある。同じインターフェース（`VlmClient`）で切り替えられる
   - **Qwen3-VL 8B（ローカル）は採用しない**。2 枚を比べると位置がずれ、小さな移動を見落とす。GPU のメモリを Isaac Sim と取り合う。ただし 1 枚の画像で指させる精度は高い（中央値 5.3px）ので、「比べる」と「位置を答える」を 2 回に分ければ改善する可能性はある（未検証）
4. **プロンプトと JSON の形式**：上の案のとおり。物体名のリストは、渡さなくても検出の精度は変わらなかったが、名前が揺れる（同じ物体が問い合わせごとに「黄色い本」「黄色い箱」になる）。後の処理で物体を名前で扱うなら、**リストを渡す**ほうがよい。「いつもの写真」から先に物体の一覧を作らせる方法も考えられる

## 設計への影響

- VLM は `VlmClient` のインターフェース（`detect(before_png, after_png, prompt) -> VlmResult`）で呼び、既定の実装を Claude Sonnet 5.5、代わりを Gemini Robotics-ER 2 とする。座標はクライアントの境界でピクセル (u, v) にそろえる
- 応答の形式は `moved_objects`（name、current_location、current_point、target_location、target_point）とする。戻し先の 3 次元位置は、`target_point` と「いつもの写真」の深度から逆投影して求める
- 天井カメラの設定（高さ 2.6m、真下向き、焦点距離 13.5mm / アパーチャ 20.955mm、1024 × 768）を基準にする
- Isaac Sim で連続して撮るときは、物体を動かした後に 150 フレーム程度進めてから撮る（残像を避ける）
- `anthropic` は 0.x に留める（Isaac Sim の `idna==3.10` との衝突）
- **残ったリスク**
  - 今回の課題は簡単すぎて、Claude と Gemini の差が精度に出なかった。似た物体（同じ色の物が 2 つ）、物体どうしの重なり、ロボットが写り込む、現実的な質感、物体の数が多い、などの条件では未検証。M1 以降で本番に近いシーンができたら、同じ評価の仕組み（`vlm_eval.py`）で再評価する
  - 上から見ると、棚の上の段など高さの違う置き場所が見分けにくい（今回は天板の上だけを使った）
  - 天井カメラを実際の部屋に付けられるかは、デモの前提として別に確認が必要
  - スマート アプリ コントロールの影響で、torch と署名のないバイナリが使えない。torch を必要とするライブラリ（学習済みの検出器など）を使う場合は、この制約を先に考える
